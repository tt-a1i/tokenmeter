# v1.0.1 性能基线

Measure-only baseline collected via the hidden `--cpu-profile` flag added in
Task 14 of the v1.0.1 ccusage-alignment plan. No optimization commitments
attached to this report — numbers here are the input for the v1.0.2
commit-or-defer decision.

## 测试环境

- **OS / CPU:** macOS 25.x (Darwin 25.3.0) · Apple Silicon
- **Go:** 1.24.x (project default)
- **DB:** `~/.agmon/data/agmon.db` (legacy path still active on this host)
  - sessions: 1,587
  - token_usage: 445,904 rows
  - tool_calls: 151,076 rows
  - file size: 549 MB (WAL not counted)
- **Command under test:** `./tm daily --cpu-profile /tmp/v1.0.1-baseline.pprof > /dev/null`
- **Profile sample duration:** 3.33 s wall-clock, 1.05 s CPU samples (31.5%)
  — the rest of the wall time is syscall / pread blocking, which `runtime/pprof`
  does not sample.

## 总耗时（wall-clock）

## Hotspots（具名 ≥3 个）

1. **`syscall.rawsyscalln` via `unix.Pread` → SQLite page reads** — 71.4% flat,
   70.5% cum. The single biggest cost is pulling B-tree pages off disk to
   stream all 445k `token_usage` rows through `scanUsageRows`. The CLI does
   a full scan because `daily` has no date floor and no covering index.

2. **`modernc.org/sqlite/lib._sqlite3VdbeExec` → `_sqlite3BtreeNext` family** —
   72.4% cum. The VDBE row-iteration loop dominates, which is the expected
   shape of "SELECT … ORDER BY timestamp ASC" over a non-indexed range. Note
   `_btreeNext` shows up at 29.5% cum, suggesting per-row cursor advance is a
   sizable share.

3. **`storage.(*DB).scanUsageRows` + `database/sql.(*Rows).Next`** — 51.4% cum
   on the storage side, 47.6% cum just on `Rows.Next()`. That's the Go-side
   binding cost of materializing every row into a `TokenUsageEntry` struct
   (10 columns scanned per row, ~445k rows). Reflection-light but called
   half a million times.

A secondary observation: **`RunAggregate` shows 55.2% cum.** Subtract storage
(51.4%) and the cli-layer work — `applyPricingMode` + `groupBy` +
`tabwriter` — accounts for ~3.8% cum. That's negligible vs. storage today.

## v1.0.2 优化候选（不承诺）

The plan's three default candidates map to the data above as follows:

- **SQLite scan 是绝对大头 → 候选 1: 在 `token_usage(timestamp DESC)` 加索引**
  — high confidence. The cold/warm gap (2.4 s → 0.8 s) is page cache; an
  index would let us avoid the full table scan when `--since` / `--until`
  bound the range, and would also lower the warm path because `daily`
  defaults to bucketing by day. Index size cost: roughly 5–10 MB on this
  DB given 445k rows. **Recommendation: implement first in v1.0.2.**

- **Row.Next 单行迁移 → 候选 2: 减少 per-row 工作**
  — medium confidence. Options: (a) pull only the columns `daily` actually
  needs (skip `agent_id`, `cache_*` if Mode != calculate); (b) replace
  reflection-driven `Scan` with raw column reads; (c) push aggregation into
  SQLite (`SELECT date(timestamp), sum(...) GROUP BY 1`). Option (c) likely
  collapses the 445k-row materialization down to 1 row per day. **Suggested
  spike: SQL-side aggregation for `daily`/`weekly`/`monthly` paths.**

- **`pricing.LoadEmbedded` 单例 → 候选 3: 已经是 once-load**
  — low ROI. We already cache `pricingMap` in `aggregate.go` as a
  package-level var, and it doesn't appear in the top-30 cum list. Closing
  this candidate as already done.

- **daemon socket dial → 候选 4: not applicable**
  — `tm daily` reads SQLite directly; no socket dial in the hot path.
  Closing as N/A.

## Reproduction

```bash
go build -o tm ./cmd/tm
./tm daily --cpu-profile /tmp/v1.0.1-baseline.pprof > /dev/null
go tool pprof -top -cum /tmp/v1.0.1-baseline.pprof | head -30
for i in 1 2 3; do /usr/bin/time -p ./tm daily > /dev/null; done
```

The `--cpu-profile` flag is intentionally hidden from `tm --help` — it lives
on `Shared` so any subcommand can write a profile, but it's not advertised
to end users.
