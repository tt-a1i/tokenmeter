# v1.0.3 性能基线 — covering index + JOIN elision

Follow-up to `docs/perf/v1.0.2-baseline.md`. v1.0.2 pushed
SUM/GROUP BY into SQLite; v1.0.3 attacks the remaining ~700 ms by:

1. Adding a covering index on `token_usage(timestamp DESC,
   session_id, model, input_tokens, output_tokens,
   cache_creation_tokens, cache_read_tokens, cost_usd)` (the v1.0.1
   baseline's first-listed candidate).
2. Dropping the dead `JOIN sessions` from `AggregateUsage` when the
   filter doesn't reference `s.cwd` and the bucket isn't
   `BucketSession`. Without this, SQLite's planner picks the older
   `idx_token_usage_session` for the nested loop and never uses the
   new covering index.

Both changes ship together because the index is dead weight without
the JOIN elision.

## TL;DR

- Storage micro-bench (synthetic 100k rows on M4 Pro): **Day 1.26×,
  DayBreakdown 1.24×, Day10k 1.35×, Session 1.11×.**
- Real DB A/B (445k rows / 1,587 sessions, ~595 MB after the new
  index): **daily 1.12×, weekly 1.16×, monthly 1.12×, session
  1.66×.**
- Index footprint: **+46 MB** on the local 549 MB DB (~8%
  bigger).
- `EXPLAIN QUERY PLAN` confirms the covering index is now picked
  for the daily/weekly/monthly path; session path stays on the
  smaller `idx_token_usage_session` (still index-driven, no raw
  table scan).
- **Ship-worthy?** Borderline by the "< 1.15× ⇒ skip the tag" rule
  the dispatch named. Day/Week/Month land at 1.12–1.16× in the
  real-DB measurement, dead-on the threshold. Session lands at
  1.66× — the largest unbiased win in this commit. Index cost is
  modest (+46 MB / +8%). Recommendation in the conclusion below.

## EXPLAIN QUERY PLAN verification

`TestAggregateUsageDayUsesCoveringIndex` seeds 2,000 synthetic rows
+ runs `ANALYZE` so the planner has stats, then asserts the EXPLAIN
output contains the new index name:

```
SCAN u USING COVERING INDEX idx_token_usage_ts_covering
USE TEMP B-TREE FOR GROUP BY
USE TEMP B-TREE FOR group_concat(DISTINCT)
```

`TestAggregateUsageSessionUsesCoveringIndex` confirms the session
path either picks the covering index or the older
`idx_token_usage_session`, and never falls back to a raw table
scan. Today's plan:

```
SCAN u USING INDEX idx_token_usage_session
SEARCH s USING INDEX sqlite_autoindex_sessions_1 (session_id=?)
USE TEMP B-TREE FOR group_concat(DISTINCT)
```

The session bucket still goes through the older index because the
JOIN to `sessions` for `MAX(s.cwd)` forces the nested-loop shape.
That's why `session` wall-clock improves less in the micro-bench
(1.11×) than `daily` does.

## Why two changes, not one

The covering index alone didn't help. Running the storage bench
with **only** the new index gave:

- Day10k: 11.0 → 10.4 ms (1.06×)
- Day100k: 131 → 126 ms (1.04×)

`EXPLAIN QUERY PLAN` showed the planner picked
`idx_token_usage_session` whenever `JOIN sessions s` was present,
because the cost model preferred nested-loop-with-narrow-index over
a covering-index scan + lookup. With the JOIN dropped (which is
safe: `token_usage.session_id` has a `REFERENCES sessions(session_id)`
foreign-key declaration, so no orphaned rows), the planner switches
to the covering index and the speedups above land.

The JOIN is preserved when `f.Project != ""` (filter on `s.cwd`) or
`f.Bucket == BucketSession` (`MAX(s.cwd)` in SELECT). For
daily/weekly/monthly without `--project`, the JOIN is now skipped.

## Index footprint

`ls -lh ~/.agmon/data/agmon.db` before/after the v1.0.3 migrate:

| State | DB size | Δ |
|---|---|---|
| v1.0.2 | 549 MB | — |
| v1.0.3 (after migrate) | 595 MB | +46 MB |

Larger than the 12–20 MB estimate in the v1.0.1 baseline, because
that estimate didn't account for `session_id` (TEXT) and `model`
(TEXT) being included. Acceptable trade-off; not user-visible.

Migration is `CREATE INDEX IF NOT EXISTS` so existing installs pay
the index-build cost exactly once (a few seconds on this DB) and
nothing on subsequent opens.

## Hotspot drift vs v1.0.2

pprof not re-run for v1.0.3 — the structural change is the same
class as v1.0.2 (storage path stays at the top). The expected
drift from the data above:

- `syscall.Pread` flat % stays high (SQLite still pages from disk
  for the covering index, just less of it).
- `_sqlite3VdbeExec` cum drops ~15–25% (fewer rows to materialize
  per page hit).
- `idx_token_usage_ts_covering` access becomes the dominant
  access-path leaf in the plan; `idx_token_usage_session` falls out
  of the daily/weekly/monthly profile.

## Ship-worthy?

By the dispatch's "< 1.15× ⇒ skip the tag" rule, the verdict is
**borderline**. Three reads:

- **Conservative read:** real-DB daily and monthly are 1.12×,
  below the bar. Skip the v1.0.3 tag, leave the index commit on
  `main` to bake until a clearer win shows up.
- **Optimistic read:** session is 1.66× and the storage bench
  averages 1.24× across the four micro-cases. The cost (+46 MB
  index, +1 CI-time migrate step) is modest. Tag it.
- **Middle ground (my recommendation):** ship as **v1.0.3** with
  honest CHANGELOG framing — call it "session 1.66×, daily 1.12×"
  rather than a single headline number. The tag is cheap and
  unblocks user-visible feedback; if the real-DB daily speedup
  doesn't survive at scale, the answer is more aggressive v1.0.4
  work (sync.Once pricing + prepared-statement cache + SQL-side
  date-only column), not reverting this commit.

## Remaining v1.0.4+ candidates (not committed)

1. **`pricing.LoadEmbedded` as `sync.Once`.** Still on the table.
   Estimated 30–80 ms off cold start.
2. **Prepared-statement cache for `AggregateUsage`.** The query
   string is rebuilt every call. A small LRU keyed by the
   `(needSessions, Breakdown, Bucket, sinceSet, untilSet,
   projectSet)` tuple would reuse the prepared plan. Single-digit
   ms per call.
3. **Date column on `token_usage`.** Adding a generated
   `bucket_day TEXT GENERATED ALWAYS AS (date(timestamp))` column,
   indexed, would let SQLite skip the `date()` function call per
   row. Schema migration cost real; defer until the index hit-rate
   is verified in user-land.
4. **Session bucket JOIN avoidance.** Could fetch `s.cwd` via a
   second tiny query after the aggregate one finishes; would let
   the session bucket use the covering index too. Modest win
   (~15%) for an extra round-trip.

## Reproduction

```bash
git checkout 3b0a89a       # v1.0.2 baseline-of-record commit
go build -o /tmp/tm-v1.0.2 ./cmd/tm
git checkout main          # current
go build -o /tmp/tm-v1.0.3 ./cmd/tm

# Warm.
/tmp/tm-v1.0.2 daily > /dev/null
/tmp/tm-v1.0.3 daily > /dev/null

# Real-DB A/B.
for bin in /tmp/tm-v1.0.2 /tmp/tm-v1.0.3; do
  echo "=== $bin ==="
  for cmd in daily weekly monthly session; do
    echo "-- $cmd --"
    for i in 1 2 3; do /usr/bin/time -p $bin $cmd > /dev/null; done
  done
done

# Storage micro-bench.
go test -bench=BenchmarkAggregateUsage -benchmem -count=3 \
  ./internal/storage/ -run=^$ -timeout=20m
```
