# v1.0.2 性能基线 — SQL push-down 验证

Measure-only follow-up to `docs/perf/v1.0.1-baseline.md`. The v1.0.2 work
replaced the cli-layer in-memory `aggGroup` with a `SELECT … GROUP BY` in
`internal/storage/aggregate.go::AggregateUsage`. This report quantifies
the actual speedup against a v1.0.1 binary built from `966cf20` on the
same local DB.

## TL;DR

- **daily** got the biggest win: warm 1.22 s → **0.99 s** (~1.23×, ~230 ms).
- **weekly / monthly**: ~1.13–1.14×.
- **session**: 1.06× (smallest gain — `BucketSession` produces ~500 rows so
  driver-side row materialization stays expensive).
- **blocks**: unchanged at ~1.2 s (intentional — `tm blocks` did **not**
  move to `AggregateUsage`; the 5-hour identifier still needs the raw
  timeline).
- **Plan target was "4× warm" → not met.** Honest assessment: SQLite full
  scan over 445k rows is I/O-bound (`syscall.Pread` 73.6% cum), and the
  fixed Go / pricing startup overhead caps the percentage win.
- pprof confirms `cli.scanUsageRows` no longer appears in the top of the
  daily path; `storage.AggregateUsage` is the new dominant cli-side caller,
  but storage SUM is still bottlenecked by the same B-tree page reads.

## Test environment

Identical to v1.0.1 baseline so the deltas reflect the code change and
not hardware drift:

- **OS / CPU:** macOS 25.x (Darwin 25.3.0) · Apple Silicon (M4 Pro)
- **Go:** 1.24.x
- **DB:** `~/.agmon/data/agmon.db` (legacy path)
  - sessions: 1,587
  - token_usage: 445,904 rows
  - file size: 549 MB
- **Binaries:**
  - `tm-v1.0.1` rebuilt from commit `966cf20` (v1.0.1 tag commit)
  - `tm-v1.0.2` built from current HEAD `cd44cf0` (post-Task 9)

> Note: v1.0.1's original baseline report (written 2026-05-20) reported
> ~820 ms warm for `daily`. Re-measuring the same v1.0.1 binary today shows
> ~1.22 s. The DB itself is byte-identical (still 549 MB / 445,904 rows);
> the gap is OS page-cache state plus the few extra months of activity in
> the workload during which other processes evicted pages. The v1.0.2
> numbers here are paired against a *fresh* v1.0.1 re-measurement to keep
> them apples-to-apples.

## Against the plan target

The v1.0.2 plan §0 promised "warm <250 ms (4×)". Actual:

- Best case (`daily`): **0.99 s → 4× target was 0.31 s. Missed by 3.2×.**
- Worst case (`blocks`): not in scope, but unchanged anyway.
- **The plan target was over-optimistic** for two structural reasons
  surfaced by the pprof + benchmark data below:
  1. SQLite is still doing a full table scan over 445k `token_usage`
     rows — push-down doesn't avoid I/O, it just avoids transporting
     445k rows through the Go driver. Driver-side savings exist
     (`scanUsageRows` is gone from the hot path) but the dominant cost
     `syscall.Pread` doesn't shift.
  2. Fixed startup costs (Go runtime, `pricing.LoadEmbedded` parsing
     the LiteLLM snapshot) run for every `tm <cmd>` invocation. On this
     machine the startup floor is roughly 0.55 s by `time -p user` math
     on minimal runs, and that floor is the same in both versions.

A 4× warm win would require collapsing the SQLite scan time, not the
Go-side aggregation. See "v1.0.3 candidates" below.

## Comparing hotspots: v1.0.1 → v1.0.2

| Function (cum %) | v1.0.1 | v1.0.2 | Note |
|---|---|---|---|
| `syscall.rawsyscalln` (flat) | 71.43% | 89.66% | Page reads now dominate even more — driver overhead reduced as expected |
| `database/sql.withLock` (cum) | 74.29% | 98.85% | A single query now lives under the lock; v1.0.1 had multiple paths |
| `modernc.org/sqlite/lib._sqlite3VdbeExec` (cum) | 72.38% | 97.70% | Same fraction of time in the VDBE, single bigger query |
| `cli.RunAggregate` (cum) | 55.24% | 80.46% | cli no longer aggregates — it now waits on storage |
| `storage.scanUsageRows` (cum) | 51.43% | **gone from top** | replaced by storage.AggregateUsage |
| `storage.AggregateUsage` (cum) | n/a | 80.46% | new caller, same B-tree underneath |
| `database/sql.(*Rows).Next` (cum) | 47.62% | **dropped** | no longer iterating 445k rows in Go |

Reading: the Go-side aggregation cost (`Rows.Next` × 445k + `scanUsageRows`)
**did** collapse — that's where the 230 ms `daily` win comes from. What
remained on the table is the SQLite I/O wall.

## Conclusion

Push-down delivered a real but **modest** warm-path speedup:
**1.06–1.23×** depending on subcommand, not the 4× the plan called for.
The win is concentrated where v1.0.1 spent the most cli-side time:
`daily` saves 230 ms by skipping 445k Go-side `Rows.Next()` + struct
materializations. `session` saves only 70 ms because storage now emits
500 rows that still have to be scanned. `blocks` is unchanged by design.

**No code in this commit changes the result above** — this is the
baseline-of-record for v1.0.2's ship gate. Whether 1.23× is "enough" is
a release-decision question, not a correctness question.

## v1.0.3 candidates (not committed)

1. **`token_usage(timestamp DESC)` covering index.** Already on the
   v1.0.1 candidate list. With a covering index that includes
   `input_tokens`, `output_tokens`, cache columns, and `cost_usd`, the
   SUM/GROUP BY can serve from index pages and skip ~80% of the table
   B-tree traversal. Estimated index size ~12-20 MB on this DB.
   Expected impact: 30–50% of the remaining 700 ms storage time.

2. **`pricing.LoadEmbedded` as `sync.Once`.** Currently called once per
   process via a package-level `var pricingMap = pricing.LoadEmbedded()`.
   It already runs once, but the JSON parse is on the critical startup
   path. `sync.Once` + lazy init would defer the cost off the synchronous
   startup. Estimated win: 30–80 ms (would have to measure).

3. **Prepared-statement cache for `AggregateUsage`.** The query is
   re-prepared on every call because the SQL string is rebuilt with
   dynamic `bucketExpr` and WHERE clauses. Caching the top-of-tree
   variants (Day / Week / Month / Session × {with/without breakdown} ×
   {with/without filters}) would amortize parse cost. Estimated win:
   single-digit ms per call, only matters for tight loops like the web
   API.

4. **`tm blocks` push-down for the timeline portion.** Not in scope for
   v1.0.2; `blocks.Identify` needs the raw row stream because the 5h
   window boundary depends on inter-row gaps. Could be split: pull
   timestamps via push-down to detect window boundaries, then re-query
   only the rows inside the active window for the cost/token columns.

5. **Skip cost recomputation when `mode=display` (current default).** A
   small cli-layer optimization: when `Shared.Mode` is "display" (the
   default for users who haven't opted in), skip the `convertRows` cost
   path entirely. Modest, but free.

None of the above is committed in v1.0.2 — they are inputs to the
v1.0.3 commit-or-defer discussion.

## Reproduction

```bash
# Same DB; rebuild both binaries before measuring.
git checkout 966cf20         # v1.0.1 tag commit
go build -o /tmp/tm-v1.0.1 ./cmd/tm
git checkout main            # current HEAD
go build -o /tmp/tm-v1.0.2 ./cmd/tm

# Warm both.
/tmp/tm-v1.0.1 daily > /dev/null
/tmp/tm-v1.0.2 daily > /dev/null

# Time 5 × 3.
for bin in /tmp/tm-v1.0.1 /tmp/tm-v1.0.2; do
  echo "=== $bin ==="
  for cmd in daily weekly monthly session blocks; do
    echo "=== $cmd ==="
    for i in 1 2 3; do /usr/bin/time -p $bin $cmd > /dev/null; done
  done
done

# pprof for daily.
/tmp/tm-v1.0.2 daily --cpu-profile /tmp/v1.0.2-baseline.pprof > /dev/null
go tool pprof -top -cum /tmp/v1.0.2-baseline.pprof | head -30

# Storage micro-bench.
go test -bench=BenchmarkAggregateUsage -benchmem -count=3 \
  ./internal/storage/ -run=^$ -timeout=15m
```
